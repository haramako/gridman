# 入力挙動の比較と設計思想

## 概要

現在のコードベースにおけるキー/マウス入力に対する挙動と、Excel の挙動を比較した仕様表。
実装時の判断基準・意図的な差異の根拠として参照すること。

## 主要な差異の詳細

### 1. Enterキー（最大の違い）
- **現在（非編集モード）**: Enterで編集モード開始
- **現在（編集モード）**: 確定して下のセルへ移動
- **Excel**: どちらのモードでも下のセルへ移動
- **方針**: 非編集モードの Enter は編集開始のままとする。編集確定後の下移動は実装済みで Excel に準拠

### 2. 列ヘッダークリック
- **現在**: 列ソート（昇順⇄降順トグル）
- **Excel**: 列全体を選択
- **方針**: Phase 1でボーナス機能として実装済みの意図的差異。ソート優先で現状維持

### 3. 未実装機能
- フィルハンドル（オートフィル）：コスト高・優先度低

## Undo/Redo スコープ仕様

### Undo 対象となる操作

| 操作 | Undo単位 | 備考 |
|------|---------|------|
| セル編集（Enter/Tab/クリック確定） | 1セル = 1ステップ | `EditCellCommand` |
| Ctrl+V ペースト（複数セル） | 全セルまとめて1ステップ | `CompositeCommand` |
| Ctrl+X カット（複数セル） | **現状: 1セルずつ**（LIN-73） | 将来的に1ステップにすべき |
| Delete/Backspace（単一セル） | 1セル = 1ステップ | |
| 行追加（+ 行追加 / 右クリック） | 1行 = 1ステップ | |
| 行削除（− 行削除 / 右クリック） | **複数行まとめて1ステップ** | `CompositeCommand` |

### Undo 対象外の操作

| 操作 | 理由 |
|------|------|
| Ctrl+S（ファイル保存） | 保存自体は不可逆とみなす。保存後もUndoスタックは残るため、保存後のUndoは可能（詳細は下記） |
| スキーマ編集（列追加・削除・変更） | `updateSchema` は CommandHistory を経由しない |
| ビュー設定変更（追加・編集・削除） | 同上 |
| プロジェクト設定変更 | 同上 |

### 保存後のUndoの扱い

保存（Ctrl+S）はUndoスタックをクリアしない。そのため：

1. 編集 → Ctrl+S → Ctrl+Z の順に操作すると、メモリ上のデータが保存前の状態に戻る
2. ファイルはすでに保存済みのため、メモリとファイルが乖離し `isDirty = true` になる
3. ユーザーは再度 Ctrl+S で保存する必要がある

**仕様として許容する**。保存後のUndoはWebアプリとして一般的な挙動であり、`isDirty` フラグで乖離が視覚的に分かる。

### Undoスタックのリセットタイミング

- **プロジェクトを開いたとき**（`loadProject`）: スタックをクリア
- **それ以外**（保存・ビュー切り替え・フィルター変更など）: スタックを保持

### Redoの失効

Undoした状態で新たな編集操作を行うと、Redoスタックが消去される。これは一般的なUndoモデルに従った仕様。

### 現状の未解決課題

- **Ctrl+X のUndo粒度**（LIN-73）: 複数セルをカットしたとき、現状は1セルずつUndoが発生する。`CompositeCommand` で1ステップにまとめるべき
- **行削除のdirtyRowIds整合**（潜在的バグ）: 行追加→保存→Undoした場合、ファイルには行が残る可能性がある。`patchTable` がrow削除を扱う仕様の明確化が必要
