# 仕様品質起因の再設計パターン

→ [[concepts/agent-patterns/index|Agent Patterns]] の一部

## 概要

issue の説明が不完全なために、実装後に設計変更や機能追加が発生するパターン。
環境問題と違い、**issue 記述の改善で防げる**。

**該当 taxonomy**: `spec-design-change`, `spec-feature-addition`

## バリエーション

### `spec-design-change` — 実装後のインターフェース設計変更

**事例**: LIN-22

初回実装後に「WarnCallback ではなく、ログレベル・文字列を引数に取る統一コールバックにしてください」という設計変更依頼が入った。「警告を出す」という要件だけでは、AI が設計を判断し、後で変更になりやすい。

**原因**: issue に「何を実装するか」は書かれているが「どんな形（インターフェース）で実装するか」が書かれていない。

### `spec-feature-addition` — 実装後の機能追加

**事例**: LIN-46, LIN-192, LIN-194（計3件）

初回実装完了後に追加対応が発生するパターン。

- **LIN-46**: 「インクリメンタルにしてください。スロットルを入れてください。」という機能追加。mvp.md に参照が書かれていても、インクリメンタル方式の詳細は明示されていなかった。
- **LIN-192**（noNonNullAssertion 除去）: 初回実装で「既存エラー」として残した DataRow.tsx の TS6133 が後から修正対象になった。「既存エラーは対象外か？」を事前確認すれば防げた。`countermeasure: none`（issue 記述の改善のみで対応可能）。
- **LIN-194**（noExplicitAny 型解消）: 実装後にステータス更新依頼が ping で来た。

## issue 記述の改善パターン

| 不足しがちな情報 | 例 |
|----------------|-----|
| インターフェース設計 | コールバックの引数、戻り値の型 |
| パフォーマンス要件 | デバウンス時間、スロットル方式 |
| UX 詳細 | Excel と同じ挙動、特定のキーへの対応 |
| 完了の定義 | どのテストが通れば完了か |

**有効な指示パターン**: 「最初に設計（インターフェース）を示してから実装してください」— LIN-43 で実証。
計画フェーズを明示することでスコープのズレを早期発見できる。

## インタラクションシナリオによる事前合意

**背景**: `spec-design-change` / `spec-feature-addition` の根本原因は、エージェントがユーザーの意図を
正しく理解しないまま実装に入ることにある（意図伝達ギャップ）。テキスト計画は UI 挙動のズレには
有効でなく、実装後に「これじゃなかった」と気づく事例が多い。

**手法**: UI 挙動が変わるタスクでは、**実装前**に 5〜10 行の操作シナリオを書いてユーザーが確認する。

```
例（セル編集フロー）:
1. セルをクリック → 選択状態
2. そのまま文字入力 → 即座に編集モード、既存値は消える
3. Enter → 確定、次のセルへ移動
4. Esc → キャンセル、元の値に戻る
```

**ルール**:
- **エージェントが書く**（ユーザーの書く負担を回避）。エージェントが「自分の解釈」を明示することで齟齬を発見できる
- **ユーザーは OK/NG するだけ**。書くのに 2〜3 分、読むのに 30 秒
- プランの構造として「インタラクションシナリオ（ここだけ確認）」を実装方針・ファイル一覧から分離する

**副産物**: シナリオはそのまま Playwright テスト（`e2e/*.spec.ts`）の given-when-then 仕様になる。
E2E テストの品質も副産物として向上する（→ [[concepts/Testing]]）。
