# 仕様品質起因の再設計パターン

→ [[concepts/agent-patterns/index|Agent Patterns]] の一部

## 概要

issue の説明が不完全なために、実装後に設計変更や機能追加が発生するパターン。
環境問題と違い、**issue 記述の改善で防げる**。

**該当 taxonomy**: `spec-design-change`, `spec-feature-addition`

## バリエーション

### `spec-design-change` — 実装後のインターフェース設計変更

**事例**: LIN-22

初回実装後に「WarnCallback ではなく、ログレベル・文字列を引数に取る統一コールバックにしてください」という設計変更依頼が入った。「警告を出す」という要件だけでは、AI が設計を判断し、後で変更になりやすい。

**原因**: issue に「何を実装するか」は書かれているが「どんな形（インターフェース）で実装するか」が書かれていない。

### `spec-feature-addition` — 実装後の機能追加

**事例**: LIN-46

初回実装完了後に「インクリメンタルにしてください。スロットルを入れてください。」という機能追加が発生。mvp.md に参照が書かれていても、インクリメンタル方式の詳細は明示されていなかった。

## issue 記述の改善パターン

| 不足しがちな情報 | 例 |
|----------------|-----|
| インターフェース設計 | コールバックの引数、戻り値の型 |
| パフォーマンス要件 | デバウンス時間、スロットル方式 |
| UX 詳細 | Excel と同じ挙動、特定のキーへの対応 |
| 完了の定義 | どのテストが通れば完了か |

**有効な指示パターン**: 「最初に設計（インターフェース）を示してから実装してください」— LIN-43 で実証。
計画フェーズを明示することでスコープのズレを早期発見できる。
