## 観察

### リポジトリ URL 設定ミスで2回詰まる

Run 1 ではリポジトリ URL が空だったためソースを読めず、設計案を提案して待機。Run 2・3 はユーザーが URL 設定を試みたが反映されておらず、Run 3（設定しなおし）でようやく実装を開始できた。接続設定はタスク開始前に動作確認しておく必要がある。

### インターフェース設計を issue に含めなかったことで再実装

Run 3 で `WarnCallback: Action<string>?` を実装したが、Run 6 で「ログレベル・文字列を引数とする一つのコールバックにしてください」という設計変更依頼が来た。issue 文には「警告を出す」とだけ書かれており、コールバックの形が指定されていなかった。エージェントが最初に設計判断を行い、後で変更になる典型パターン。

### 対策の現状

AGENTS.md の「大規模タスクの進め方」に「新しいインターフェース・アーキテクチャの設計判断が必要なら中止・分割依頼」が記載済み。このルールに従えば Run 1 で設計を確認してから実装に入れるため、後の設計変更 run を防ぎやすい。

### セキュリティ懸念の確認

Run 4 では「Dropbox のファイルに対して find.exe を実行したか？」という確認コメントが届いた。エージェントのファイルアクセス範囲についてユーザーが懸念を持ったケース。エージェントはプロジェクトディレクトリのみを検索していたことを説明して解消。

## 教訓

1. **インターフェース設計が必要なら中止して確認する** — AGENTS.md の「新しいインターフェース・アーキテクチャの設計判断が必要なら実行を中止してタスク分割を依頼」ルールを守ることで、後の設計変更 run を防げる（現在は対策済み）。
2. **外部リポジトリへのアクセス設定はタスク開始前に動作確認** — 接続失敗は実装と無関係な run 増加を招く。issue アサイン前にリポジトリ URL が設定済みかを確認する。
3. **ファイルアクセス範囲の透明性** — エージェントがどのパスを検索したかを run 結果に明示すると、ユーザーの懸念を事前に防ぎやすい。
