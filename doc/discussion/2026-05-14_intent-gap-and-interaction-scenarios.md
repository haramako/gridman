# 意図伝達ギャップとインタラクションシナリオによる事前合意

**日付**: 2026-05-14  
**関連ファイル**: `AGENTS.md`, `wiki/wiki/concepts/agent-patterns/Spec_Quality.md`

## 相談内容

multica ワークフローにおける失敗の主因は、技術的エラー（quota 切れ・platform-artifact）よりも「意図伝達ギャップ」であるという問題意識から出発。エージェントがユーザーの意図を正しく理解しないまま実装し、完了後に「これじゃなかった」と気づくケースが多い。

「指示の精度を上げる仕組み、もしくは精度の高い指示を引き出すためのQ&Aの仕組みが必要ではないか」という仮説が提起された。

## 検討した選択肢

**スクリーンショットによる視覚レビュー（実装後確認）**  
→ UI の見た目には有効だが、挙動（インタラクション）の確認には遅すぎる。実装に多くの時間を使った後になるため採用しない。

**テキスト計画の Plan-first 強制**  
→ ロジック変更には有効だが、UI挙動の確認にはテキストが不向きで、かつユーザーが詳細なプランを読む時間が取れない。

**インタラクションシナリオ（採用）**  
実装前に5〜10行の操作シナリオを書いて合意する。例:
```
1. セルをクリック → 選択状態
2. そのまま文字入力 → 即座に編集モード、既存値は消える
3. Enter → 確定、次のセルへ移動
4. Esc → キャンセル、元の値に戻る
```
書くのに2〜3分、読むのに30秒。これは人間のプロトタイピング（紙ワイヤーフレームによる事前確認）と構造的に同じ。

## 決定事項

1. **UI挙動が変わるタスクでは、実装前にインタラクションシナリオを書いてユーザーが確認する** — 実装後の手戻りを最小化するため。シナリオは「最小コストで意思決定に必要な情報を引き出す」プロトタイピングと同じ役割を果たす

2. **シナリオはエージェントが書く（ユーザーが書くのではない）** — エージェントが「自分の解釈」を明示することで、齟齬を発見できる。ユーザーが仕様を書く負担を避けるため。ユーザーは「確認してOK/NG」するだけでよい

3. **Plan の構造化**: UIの挙動が変わるタスクのプランは「インタラクションシナリオ（ここだけ確認）」を明示的に含める。実装方針やファイル一覧は確認不要として分離する

4. **シナリオはそのままE2Eテスト仕様になる** — Playwright テスト（`e2e/*.spec.ts`）の given-when-then と対応する。副産物として E2Eテスト品質も向上する
