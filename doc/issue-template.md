# Multica issue テンプレート

Multica で AI エージェントに依頼するときのテンプレート。
仕様の後追い変更（`spec-design-change`, `spec-feature-addition`）を防ぐため、
実装前に確定させるべき情報を明示する。

---

## バグ修正

```
## 現象

（再現手順・期待動作・実際の動作）

## 完了の定義

- [ ] （どのテストが通れば完了か）
- [ ] E2E テストが通ること
```

---

## 機能追加・実装

```
## やること

（何を実装するか）

## インターフェース / 設計

（関数・コールバック・コンポーネントの I/F を事前に決めておく場合はここに書く）
（決めない場合は「最初に設計案を示してから実装してください」と書く）

## 仕様の詳細

- UX: （Excel との差異、特定キーの挙動など）
- パフォーマンス: （デバウンス・スロットル要件があれば）
- スコープ外: （やらないことを明示しておくと機能追加の後追いを防げる）

## 完了の定義

- [ ] （どのテストが通れば完了か）
- [ ] E2E テストが通ること
```

---

## 運用メモ

- **インターフェースを決めない場合** は「最初に設計案を示してから実装してください」を必ず入れる（LIN-43 で実証済み）
- **スコープを限定したいとき** は「スコープ外」に書いておくと機能追加の後追いが減る（LIN-46 教訓）
- **quota 回復後の再起動確認** には `ping` を使う（"いかがです？" などの自然言語より機械的に検出しやすい）
