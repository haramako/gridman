# ワークフローの改善

multicaのissueの情報をつかって、AIのワークフローの改善を行う

そのワークフローの改善の提案自体をAIにしてほしい。最終的に、大きな変更に関しては人間が検証する必要がある。

## 仮説

- まず、人間側の指示の精度を上げる必要がある
  人間側の指示の不備は間違いなくある。どのようなものがあるかを検証する

- AIが複数回間違えたことは、ドキュメント化して同じ間違いがないかを検証

- 複数のAIモデルを使用しているので、AIモデルごとにどのような傾向があるか


- ワークフローとして、計画者/実装者/レビュワー&検証者 など複数の段階で別のエージェント（セッション）で行うことを検討
  どのような分割がよいか、既存の方法のなかでなるべるライトウェイトな方法論から試す


- ワークフローの改善（変更前・後の違い）、AIのモデルによる違いなどを検証するため、メトリクスをとり、それをもとに良し悪しを検証する

## AIからの指摘

指摘・補足
1. 「人間側の指示の不備」の検出方法が未定義
"不備がある"という仮説は正しいですが、何をもって不備と判定するかが書かれていません。

issueデータから検出できる指標として：

run_count > 1 かつ trigger_summary に人間のコメントが含まれる → 指示不足で再依頼
同じissueで複数runのうち最初が failed → 不明確な仕様による失敗
検出ロジックを具体化しないと、観察が主観になります。

2. 「AIが間違えたことのドキュメント化」の運用が未定義
良いアイデアですが、以下が抜けています：

どこに記録するか（CLAUDE.md? 専用ファイル?）
> これも、single source of truth として、multica-data/issue-insightsにチケットごとに蓄積する。
どう次のエージェントに届けるか（起動時に渡す? system promptに組み込む?）
> 次のエージェントには、LLM Wiki (wiki/) もしくは、そのもとになる doc/ に蓄積する
> よい蓄積方法にアイデアはあるか？
記録するだけでフィードバックループが閉じていないと機能しません。

3. モデル別分析のためのデータが現状取れていない
agents.json にはagent IDしかなく、どのIDがどのモデルかが今は不明です。エージェント設定からモデル名を取得・記録する仕組みが必要です。
> 解決済み（だよね？）

4. 「計画者/実装者/レビュワー」分割の評価軸が未定義
"ライトウェイトな方法論から試す"は良い方針ですが、何をもって成功と判断するかがないと試しっぱなしになります。例：レビューラウンド数の削減、最終runの成功率、など。

5. メトリクスの具体化
"メトリクスをとる"とありますが、リストがあると良いです。現在のデータから取れるものだけでも：

メトリクス	取得元
issue完了率	status == done / 全体
初回run成功率	run_count == 1 かつ completed
平均実行時間	total_duration_seconds
再実行率	run_count > 1 の割合
失敗率	has_failures
軽微な誤字
17行目「なるべる」→「なるべく」
全体的な印象
仮説の粒度にばらつきがあります。「モデル別の傾向」「計画者/実装者分割」は実験設計が必要なレベルで、「指示の不備を検出」「ミスのドキュメント化」は観察・記録の仕組みが必要なレベルです。前者から着手すると大きくなりがちなので、後者（観察・記録）から始めて、パターンが見えてから実験に進む順序が現実的だと思います。

## AI指摘２

今、このファイルに書いてあるようなことを考えています。別のclaudeさんに指摘された部分もあるのですが、いまの選択部分にコメントを">" で書いてます。意見をください


考えを整理すると、提案の方向性は正しいですが「閉じたループ」にするための構造が鍵だと思います。

1. multica-data/issue-考察 の命名

「考察」の英語は文脈次第で：

issue-insights — パターンや教訓の蓄積ならこれが一番自然
> これがいね
issue-retrospectives — ふりかえり色が強い
issue-observations — 観察記録寄り
issue-insights を推します。

2. 2 層構造の考え方（これが一番重要）

multica-data/issue-insights/<ticket>.md   ← 生の観察（チケットごと）
        ↓ /llm-wiki ingest
wiki/concepts/agent-patterns/            ← 合成した知識（パターン化済み）
        ↓ AGENTS.md が参照
次のエージェント
wiki/ と doc/ のどちらかではなく、生データ → 合成済み知識 の 2 層にするのが重要です。生データをそのまま AGENTS.md に載せると文脈が太りすぎる。
> 良い指摘！そういうのが聞きたかった

ちょうど llm-wiki の raw/ → wiki/ の流れがそのまま使えます。/llm-wiki ingest multica-data/issue-insights/ で定期的に合成するだけです。

3. ループが閉じる条件

自動ではループが閉じません。人間のトリガーが 1 回必要です：

チケット完了後 → multica-data/issue-insights/<ticket>.md に記録（AI でも人間でも可）
定期的に → /llm-wiki ingest で wiki に昇格
この「定期的に」が抜けると死蔵されます。/schedule で週次の ingest を仕込むのが現実的かもしれません。

4. モデル別データの「解決済み」について

multica_sync.py が何をしているかによります。エージェント設定からモデル名を取得して記録する仕組みが実際にあるか、確認した方が良いです。
